# 任务日志逐章节填写指南

本文件对 `SKILL.md` 中引用的模板各章节提供详细填写指导，包含好坏示例对照。
Agent 在填写日志遇到不确定时，可按需加载本文件参考。

> **加载提示**：本文件为按需引用，不要每次执行 skill 都全量读取。仅当某章节不知如何填写时再加载对应部分。

---

## Front-matter（元信息）

### 填写要点
- `task_id`：项目内唯一，格式 `TASK-XXXX`，四位补零
- `session_id`：如 Agent 环境暴露了会话 ID 则填写；如环境未暴露，统一留空，不要猜测
- `status`：只能取 `completed | partial | failed | cancelled`
  - `partial`：部分完成，有未达成的完成标准
  - `failed`：任务目标未实现
- `tags`：优先从受控词表取值，可多选：`bugfix` `feature` `refactor` `config` `research` `test` `doc` `chore` `hotfix`
- `key_files`：写相对项目根目录的路径，不写绝对路径
- `prev_task`：如果是延续上一个任务的后续工作，填写上一个 task_id
- 空值约定：字符串可选字段统一用 `""`，列表可选字段统一用 `[]`

### 坏示例
```yaml
tags: [一些bug修复]          # 不在受控词表
key_files: [C:\Users\...\src\app.ts]  # 用了绝对路径
status: done                  # 无效值，枚举中不存在，应为 completed
```

### 好示例
```yaml
tags: [bugfix, config]
key_files: [src/auth/login.ts, src/config/index.ts]
status: completed
prev_task: TASK-0006
```

## 1. 任务上下文

### 1.1 原始指令
**核心原则：原样保留，不做润色。**

用户的原始措辞可能含糊、有歧义，这本身就是有价值的信息——它反映了需求的真实形态。
Agent 对指令的理解和拆解决策，放在 1.2 中记录。

### 1.2 任务拆解
记录 Agent 如何理解并分解任务。即使任务是单步的，也写一行说明"未拆解，单步任务"。

依赖列写序号，多个用逗号分隔。无依赖写 `-`。

### 1.3 完成标准
**这是最容易被忽略但最重要的字段。**

在任务开始时就应明确"什么算完成"。如果用户指令本身没有明确标准，Agent 应在日志中记录该事实，并在「完成标准核对」中说明推断依据或未确认的原因。事后核对时，未达成的标准要说明原因。

## 2. 执行轨迹

### 结构顺序
模板已调整为**先写步骤概要，再展开关键步骤**：
- 2.1 步骤概要区：合并所有顺利步骤
- 2.2+ 关键步骤块：仅展开关键决策点和异常

### 何时展开为完整步骤块
- 出现了分叉决策（选 A 还是 B，为什么选了这个）
- 遇到了异常或失败
- 做了非显而易见的操作（如手动编辑了配置、绕过了某个机制）

### 何时合并到"步骤概要区"
- 顺利的文件读取/写入
- 成功通过的构建/测试/lint 命令
- 纯确认性的操作（查看文件确认内容）

### 决策理由的写法
- 好："选择修改 login.ts 而非中间件，因为 token 生成逻辑只在 login.ts 中，改中间件会影响其他入口"
- 坏："因为这样更好" / "根据最佳实践"

### 假设的写法
记录行动时基于的未验证假设。事后如果假设被推翻，这是重要线索。
- 好："假设项目的 ORM 是 Prisma（基于 package.json 中的依赖），未验证即开始写迁移脚本"
- 如果后续发现实际是 Drizzle，这就是一个关键信息发现

### 命令输出
只保留摘要（关键行），不粘贴完整 stdout/stderr。例如：
- 好：`构建通过，0 errors`
- 坏：粘贴 200 行完整构建日志

## 3. 遇到的问题与解决

### 现象 vs 根因
- 现象：报错说什么、行为哪里不对 — 客观描述
- 根因：为什么会出现这个现象 — 分析判断

常见错误：把现象当根因。如"找不到模块"是现象，"tsconfig paths 未配置"才是根因。

### 尝试过的方案表
**一定要记录失败的尝试。** 格式：

| 序号 | 方案 | 结果 | 备注 |
|------|------|------|------|
| 1 | 删除 node_modules 重装 | 失败 | 问题依旧，排除依赖损坏 |
| 2 | 修改 tsconfig paths | 失败 | paths 已正确，问题在别处 |
| 3 | 在 vite.config 中添加 alias | 成功 | 实际构建工具是 Vite 不是 tsc |

失败方案的"备注"列要写明为什么失败、排除了什么可能性，这是逐步逼近根因的过程记录。

### 遗留问题
暂时绕过但未根治的问题，用 TODO 标记。格式：
- [ ] {问题描述} — {临时绕过方式} — {建议的根治方向}

## 4. 信息发现

### 关键发现
执行过程中了解到的事实，即使与当前任务不直接相关，但有助于理解项目或避免未来踩坑。

- 好："项目实际使用 Vite 而非 Webpack（尽管 README 中提到 Webpack）"
- 好："数据库迁移工具用的是 Drizzle Kit，不是 Prisma Migrate"
- 坏："项目用 TypeScript"（太显而易见）

### 与预期不符之处
文档/直觉/约定与实际不一致的地方。这类信息对后续任务最有价值。

### 反模式 / 陷阱
踩过的坑 + 避让方法。写法建议：
- {坑的描述} → {避让方法}
- 例：`lint 会拒绝 any 类型 → 不要用 any，用 unknown + 类型守卫`

### 无发现时
若本次任务确实无实质性发现，可标注「无」，不必强行编造或进行二次迭代。

## 5. 验证与结果

### 验证方式表
如实记录。如果没跑测试就不要写"跑了测试"。
- 如果任务未经任何验证就结束，在此表中写一行"未验证"并说明原因
- 验证证据要具体：不写"测试通过"，写"5 passed, 0 failed, 2 skipped"

### 产出物清单
列出所有新增/修改/删除的文件。"操作"列取值：`新增 | 修改 | 删除`。

### 完成标准核对
与 1.3 中的完成标准一一对应。未完成项必须说明原因。

## 6. 回顾笔记

此章节可选，但鼓励填写。重点关注：
- **做得好的**：值得在后续任务中保持的做法
- **可改进的**：走了弯路、浪费时间的地方
- **如果重来会怎么做**：基于复盘的最优路径

这是知识从"经历"提炼为"经验"的环节。

## 通用写作原则

### 记录优先级

当简洁与完整产生冲突时，按以下优先级取舍：

> **关键决策与异常 > 失败尝试 > 验证结果 > 顺利步骤**

在保证关键信息完整的前提下，尽量简洁。不要因为"简洁优先"而省略失败尝试和关键决策的记录。

### 其他原则

1. **引用具体位置**：提到代码变更时写 `文件路径:行号`，方便跳转
2. **不伪造**：不确定的信息标注"（未确认）"，不要编造
3. **时间戳用 HH:MM**：不需要精确到秒，但步骤之间的相对顺序要清晰
4. **避免复制 Agent 原始输出**：提炼关键信息，不要把整段工具输出粘进去
5. **敏感信息先脱敏**：见 SKILL.md 原则 1，脱敏优先于"原样记录"

# Task Log — 任务执行时序记录

## 概述

本 skill 指导 Agent 在任务执行完毕（或中断、失败）后，基于模板生成一份结构化的任务日志。
日志同时服务于两个目的：

1. **人类可读**：用高信噪比的格式替代 Agent 原始输出的冗长过程
2. **Agent 可回溯**：后续任务中 Agent 可读取历史日志，快速恢复上下文、避开已知陷阱

## 何时触发

在以下时机生成本次任务的日志：

- 用户显式要求「记录任务」「整理过程」「写日志」
- 任务完成后自动触发（需用户在 Agent 配置中设定本 skill 为 post-task hook）
- 任务失败或中途取消时，记录已执行部分

## 工作流程

### 第 1 步：确定日志存放位置

- 默认存放目录：项目根目录下的 `task-logs/`
- 文件命名：`TASK-{编号}-{简短slug}.md`，如 `TASK-0007-fix-login-bug.md`
- **路径约束**：日志文件必须且只能写在 `task-logs/` 目录内，使用相对路径，禁止包含 `..` 等路径遍历片段
- **slug 校验**：slug 只能包含小写字母、数字、连字符（`-`）和下划线（`_`），长度不超过 50 字符
- 若 `task-logs/` 不存在，通过文件写入工具自动创建（避免不必要的 Bash 调用）
- **编号规则**：使用 `Glob` 匹配 `task-logs/TASK-*.md`，按文件名排序提取最大编号后 +1；若无已有日志则从 `0001` 开始。若目标文件名已存在，继续递增编号直至可用

### 第 2 步：读取模板

读取模板文件：
```
assets/TEMPLATE.md
```

将其内容作为骨架，填充本次任务的实际信息。

### 第 3 步：填充日志内容

按模板结构逐节填写。填充时遵循以下核心原则：

#### 原则 1：安全与隐私（最高优先级）
- 报错原文、配置文件片段、环境变量输出中若包含敏感信息，必须先用 `[REDACTED]` 替换后再记录，并在脱敏处注明「已脱敏」
- 以下内容一律不记录：私钥、密码、Token、数据库连接字符串、内部系统 URL、个人身份信息（PII：姓名、手机号、邮箱、身份证号等）、未公开的业务数据
- 无法判断是否敏感时，保守处理（替换或省略）
- 任务日志可能包含项目内部信息，应与源代码同等保密，避免共享到公共仓库或聊天窗口

#### 原则 2：事实与判断分离
- **事实层**：报错原文（脱敏后）、命令输出摘要、文件路径、时间戳 — 原样记录，不做改写
- **判断层**：根因分析、决策理由、假设 — 明确标注为分析，可与事实区分
- 注意：事实层中的敏感信息先脱敏再记录（见原则 1），脱敏优先于"原样记录"

#### 原则 3：失败比成功重要
- 记录所有尝试过的方案，**包括失败的**
- 失败方案要写明「为什么失败」，这是最有复用价值的知识
- 顺利步骤可合并为一行概要，不要逐步展开

#### 原则 4：控制信噪比与日志长度
- 关键决策点 + 异常点：密集记录（动作、理由、假设、结果全部展开）
- 常规顺利步骤：合并到「步骤概要区」，一行带过
- 纯信息性的工具调用（如读取文件确认内容）：不必单独列步骤
- 命令输出只保留摘要（关键行），不粘贴完整 stdout/stderr
- 单条日志原则上不超过 500 行；若超出，按"续篇机制"拆分（见边缘情况）

#### 原则 5：可检索性
- YAML front-matter 必须完整填写（task_id、tags、key_files、related_tasks）
- tags 优先从受控词表选择：`bugfix` `feature` `refactor` `config` `research` `test` `doc` `chore` `hotfix`。必要时可新增，但应在日志中注明新增理由
- key_files 列出本次任务读写过的所有文件路径（相对路径）

### 第 4 步：补充信息发现

这是区别于「流水账」的关键章节。填写时问自己：

- 执行中有没有发现「和文档/直觉/预期不符」的事？
- 有没有踩到坑、走了弯路？下次怎么避免？
- 有没有了解到关于本项目的关键事实（框架选择、约定、隐藏配置）？

鼓励充分填写。若本次任务确实无实质性发现，可标注「无」，不必强行编造。

### 第 5 步：验证记录

如实记录验证手段和结果。如果任务未经充分验证就结束，在「完成标准核对」中标记未完成项并说明原因。**不要伪造验证结果。**

### 第 6 步：写入文件并告知用户

将填充后的日志写入 `task-logs/TASK-{编号}-{slug}.md`，然后向用户输出：

- 日志文件路径
- 任务编号
- 一句话状态摘要（如「TASK-0007 已完成，2 个问题已解决，1 个遗留 TODO」）

## 引用文件加载策略

执行本 skill 时：

1. **必读**：`assets/TEMPLATE.md` — 日志骨架
2. **按需读**：`references/RECORDING_GUIDE.md` — 仅在遇到填写歧义、不确定某章节如何填写时加载，**不要每次执行都全量读取**
3. `SKILL.md` 本身已包含各原则的要点，通常无需加载引用文件即可完成填写

## 输入与输出示例

### 输入

用户完成一个修复登录 bug 的任务后，触发本 skill。Agent 回顾本次会话：
- 读了 `src/auth/login.ts` 和 `src/config.ts`
- 发现问题根因是 token 过期时间硬编码
- 尝试方案 1（修改配置文件）失败，因为配置在运行时被覆盖
- 最终方案：在 `login.ts:42` 改为从环境变量读取
- 运行 `npm test` 通过

### 输出文件

```
task-logs/TASK-0007-fix-login-bug.md
```

文件内容基于 `assets/TEMPLATE.md` 填充，包含完整的 front-matter 和六个章节。

## 常见边缘情况

### 任务失败/中途取消
- 仍然生成日志，`status` 设为 `failed` 或 `cancelled`
- 执行轨迹记录到中断点为止
- 在「遗留问题」中记录失败原因和可能的后续方向

### 任务极简（单文件单行修改）
- 日志可以精简，但 front-matter 和「完成标准」不可省略
- 执行轨迹可合并为一两行，问题章节若无问题可写「无」

### 多次会话接力同一任务
- **同一任务多会话**：`task_id` 不变，在日志末尾追加新会话段落，不填 `prev_task`
- **新任务依赖旧任务结果**：`task_id` 递增，`prev_task` 填旧任务 ID

### 日志文件过大（续篇机制）
- 当日志文件超过 500 行时，创建续篇文件：`TASK-{编号}-{slug}-part2.md`、`-part3.md`…
- 在 front-matter 的 `related_tasks` 中关联续篇/前篇文件

### 涉及敏感信息
- 见原则 1（安全与隐私），脱敏优先于一切记录原则

### 日志保留与归档
- 任务日志应与源代码同等保密，避免提交到公共仓库
- 长期项目可定期归档或清理 90 天前的日志（由用户决定，本 skill 不自动删除）
